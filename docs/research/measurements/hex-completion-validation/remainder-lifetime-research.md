# Finding the remaining subset-lifetime segment

ROOT coordinator primary/source research, 2026-11-11. This is a design boundary under review, not an implementation or native acceptance claim. Current policy7d7e0855/rulesdf2acf47 applies. Existing L1/L2/L3 owners perform the background source/contract work; no new agent or manager is created.

The exact d87 integration now passes the one-of-two workload selection, full-P backing hold, one-consumer reservation/cancel, canonical source-release gate and selected-VM receipt controls. The sibling original fails at its first pre-release refusal assertion (NoRoom versus NoGpu), before any terminal freshness oracle. That is not a live reproduction of stale sibling admission. Raw logs and source are preserved in continuation-selected-subset-d87. Separately, 8c originals reproduce that backend-wide unavailable masking prevents a legitimate Prepared provisioning grant and suppresses an unrelated key. Those are distinct required corrections.

The missing later segment is producer lifetime: retaining old source P for a BoxS receipt while admitting a separately charged, newly observed remainder R. Existing RouteOffer and RouteReceipt already carry both RouteKey and optional BackingKey. Capacity::check_route_parts currently rejects equal RouteKey unconditionally, including different source lifetimes. Index and normalization therefore need deliberate qualified identity semantics; merely shortening P.devices or reusing old observations cannot implement this behavior. These conclusions are source observations from current API runtime.rs, sim index/routes.rs and runtime guest pool code, not a native VM reproduction.

Primary comparison: Kubernetes DRA separates inventory advertisement, claim allocation and node preparation. Its allocation/status device identity includes driver, pool, device and optional share identity; status must refer to the allocated identity. This supports retaining the allocation lifetime separately from an observation or readiness update, rather than making a route predicate the sole lifetime key. It does not prove Hex behavior. See the [official ResourceClaim API](https://kubernetes.io/docs/reference/kubernetes-api/resource/resource-claim-v1/) and [DRA lifecycle overview](https://kubernetes.io/docs/concepts/resource-management/dynamic-resource-allocation/).

The chosen narrow identity shape for owner coordination is the existing (RouteKey, BackingKey) tuple; no new DTO/wire/selector/ledger. Retained ReleasedP remains accounting/recovery-only with fresh admission clear, while a new exact-set-bound R has its own canonical key/generation, same validated family configuration/profile, and charge before native boot. Invalid/conflicting qualified receipts and physical overlaps still refuse. Old P data cannot certify R freshness or the newly selected VM.

Two producer alternatives remain under comparison. An explicit prepare(route, IDs) RPC would make Index request a subset, but adds protocol/control authority absent from the current grant API. A single deterministic complement of configured IDs minus canonical retained claims can reuse existing prepare/Index grant without a workload picker; however its canonical snapshot must be guarded, and it must solve expansion/coalescing when a Box ends while an R observer is still live. Silently killing R, returning its charge early, spawning all subsets or leaving permanent fragmentation would each fail the contract. Owners must seal that lifecycle before implementation. Existing count/route bounds remain bounds, not a new tuning allowance.

Required counterexamples: two disjoint consumers cannot share one dedicated source; unobserved R never admits fresh work; old P recovery remains exact after new R; malformed/mismatched profile or native identity refuses; owner crash at each publication retains all affected claims; a released Box can eventually allow a larger fresh set through actual observation, without bypassing native release/charging. Actual selected-VM output, foreign-device refusal and physical/resource return remain native obligations. Current research has no performance, leak-free or completed portability conclusion.
